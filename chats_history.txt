DocuMind — AI Engineer Interview Walkthrough
1. One-line pitch
DocuMind is a multi-tenant RAG application for Q&A over technical documentation. Users upload docs (PDF / Markdown / HTML), the system ingests and embeds them, and then they ask natural-language questions. The answer engine isn't a plain linear RAG chain — it's an agentic pipeline built on LangGraph that interprets the query, retrieves, reranks, and conditionally retries retrieval before synthesizing a grounded, cited answer.

The sample corpus is the FastAPI documentation, which is a good choice because it mixes prose, API reference, and embedded code — a realistic retrieval challenge.

2. The journey: prototype → finished system
I'd frame the build story in phases, because interviewers want to see engineering judgment, not just a feature list:

Phase 1 — Skeleton & contracts. FastAPI app with three routers (/auth, /documents, /query), Pydantic schemas defining the API contract separately from the DB models (so storage shape and API shape can diverge), and Postgres + pgvector as the datastore. JWT auth from day one because everything is multi-tenant.

Phase 2 — Ingestion pipeline. Parse → chunk → embed → store. Built synchronously inside the upload endpoint (fine for MVP file sizes; a background queue is the noted next step if latency becomes a problem).

Phase 3 — Basic RAG. Vector-only retrieval with cosine distance in pgvector, then straight to the LLM. This is the baseline.

Phase 4 — Make it agentic. This is where it gets interesting and is the part I'd spend the most interview time on. Wrapped the flow in a LangGraph state machine, added a query-interpretation node, a Cohere reranking stage, and a conditional retrieval retry loop that widens the search when confidence is low.

Phase 5 — Grounding & transparency. Strict grounding prompt ("answer ONLY from context, say so if it's not there"), inline citations back to source doc + section, and a per-node execution trace returned to the frontend so the UI shows the real pipeline, not a simulation.

Phase 6 — Evaluation. A reproducible RAGAS harness measuring faithfulness, answer relevancy, context precision, and context recall — deliberately split into two phases to work around a dependency conflict (more below).

4. Agent architecture (the core — spend most time here)
The agent lives in 
graph.py
. It's a LangGraph StateGraph.

The shared state
Every node reads and writes one TypedDict:

python

class AgentState(TypedDict):
    question: str
    user_id: str
    interpreted_query: Optional[str]
    retrieved_chunks: Optional[List[dict]]
    reranked_chunks: Optional[List[dict]]
    retrieval_attempts: int
    answer: Optional[str]
    citations: Optional[List[dict]]
    trace: List[dict]   # one entry per node: {stage, summary, detail}
Key LangGraph idiom to mention: nodes don't mutate state in place; they return a partial dict that LangGraph merges. That's why the trace list is accumulated with state.get("trace", []) + [entry] in every node — it builds up an audit trail as it flows through.

The graph shape

interpret_query → retrieve → rerank → [route] → synthesize → END
                     ^________________________|
                        (retry on low confidence)
Four nodes, entry at interpret_query, and — the differentiator — a conditional edge after rerank that can loop back to retrieve.

What each node does
interpret_query — LLM rewrites the raw user question into a short, keyword-rich retrieval query (expands abbreviations, strips conversational filler). The question a human asks and the string that searches best are not the same thing, so this cleans the input before it hits the vector store.

retrieve — Embeds the interpreted query, then runs a pgvector cosine-distance kNN search scoped to the current user's documents only (Document.owner_id == user_id — that's where multi-tenant isolation is enforced). Starts at top_k = 8.

rerank — Passes candidates through Cohere's cross-encoder reranker, which scores query↔chunk relevance far more accurately than raw vector distance, and keeps the top 3. This is the classic two-stage retrieve-then-rerank pattern: vector search optimizes recall (cast a wide net cheaply), the reranker optimizes precision (expensive but accurate on a small set).

synthesize — Builds a context block formatted as [Source: {doc} § {section}] per chunk, calls the LLM with a strict grounding system prompt, and returns the answer plus structured citations.

The conditional retrieval loop (the standout feature)
This is what I'd lead with because it elevates the project from "RAG chain" to "agent":

python

MAX_RETRIEVAL_ATTEMPTS = 2
RERANK_CONFIDENCE_THRESHOLD = 0.5

def route_after_rerank(state):
    reranked = state.get("reranked_chunks") or []
    attempts = state.get("retrieval_attempts", 0)
    top_score = max((c.get("relevance_score", 0) for c in reranked), default=0)
    if not reranked or (top_score < 0.5 and attempts < MAX_RETRIEVAL_ATTEMPTS):
        return "retry"
    return "synthesize"
If the best reranked chunk scores below 0.5 (Cohere's relevance score) and we haven't hit the 2-attempt cap, the graph loops back to retrieve — and critically, the retriever widens the net on each retry: top_k = 8 + attempts × 6, so 8 → 14 → 20. A weak first pass on an ambiguous question gets one broader second chance before the system commits to an answer.

Two bits of judgment to highlight:

The loop is bounded. An unbounded agent loop just burns API calls without improving the answer, so it's hard-capped at 2 attempts and then synthesizes with whatever it has.
The retry does something different. Looping back with the same query would be pointless; widening top_k means the retry actually explores more of the corpus.
Observability
Each node appends a {stage, summary, detail} entry to trace, and the API returns it in the response. The frontend renders the actual pipeline execution — including whether a retry fired — so it's genuine transparency, not a canned animation. LangSmith tracing is also wired in as an option.

5. RAG implementation details
Chunking — strategy and the "why" (
chunker.py
)
Parameters: MAX_CHUNK_CHARS = 1800, OVERLAP_CHARS = 200.

The strategy is structure-aware with a fixed-size fallback:

Markdown/HTML → split on H1–H3 headers. The reasoning: in documentation, a section is a natural semantic unit. Splitting on headers means a chunk never straddles two unrelated topics, and the section title comes along for free as citation metadata. There's even a guard (_real_header_matches) that ignores # lines inside fenced code blocks so a bash comment like # run this isn't mistaken for a Markdown heading — a nice detail showing the chunker was tuned to real docs.
PDF → fixed-size with overlap. Once a PDF is flattened to plain text there's no reliable structure, so it falls back to fixed windows. Any header section that's still over 1800 chars also gets sub-split this way.
Why these numbers:

1800 chars is large enough to hold a complete API-reference section (so the answer isn't fragmented) but small enough to keep retrieval precise and fit comfortably in the reranker and LLM context.
200-char overlap preserves continuity across boundaries so an answer that spans a split point isn't cut in half.
One more parsing nuance worth mentioning: for Markdown, the parser does "resolve-then-chunk" — it inlines FastAPI-style {* path/to/file.py *} code-snippet macros before chunking, so code and the prose explaining it land in the same chunk instead of being separated.

Embeddings
Active provider is VoyageAI voyage-4-lite, output-dimension-matched to the pgvector column so switching providers never requires a schema migration. LLM calls run at temperature 0 for determinism — important for a factual Q&A system and for reproducible evaluation.

6. Where data is stored
Everything is in PostgreSQL — there is no separate vector database. pgvector stores the embeddings in-row. Four tables:

users — id, email (unique), bcrypt-hashed password
documents — id, owner_id (FK), filename, doc_type
chunks — id, document_id (FK), content, embedding = Vector(512), section (for citations). This table is the vector store.
query_logs — question/answer history per user
Retrieval uses pgvector's cosine_distance operator. For MVP scale it's an exact nearest-neighbor scan — no IVFFlat/HNSW index yet, which is an honest "next step" to raise if asked about scaling.

Keeping vectors and relational data in one Postgres instance is a deliberate simplicity call: one datastore, transactional consistency between a document and its chunks, and no extra infra to operate. The trade-off is that it won't match a dedicated vector DB at very large scale — a good thing to acknowledge proactively.

7. Evaluation (RAGAS, two-phase)
Metrics: faithfulness, answer relevancy, context precision, context recall — against a hand-written EVAL_SET with ground-truth references (not model-generated, so recall and quality metrics have something real to compare against).

The interesting engineering story: it's split into two phases running in two separate virtualenvs:

Phase 1 (collect.py) runs in the app venv, invokes the real agent graph for every eval question, and dumps plain JSON.
Phase 2 (score.py) runs in a RAGAS-only venv with zero imports from the app, reads that JSON, and scores it.
Why: RAGAS pulls an old langchain-community that needs langchain-core <1, which conflicts with LangGraph needing langchain-core ≥1.4. Rather than fight the dependency resolver, generation and scoring were decoupled — which also happens to be cleaner separation of concerns ("produce answers" vs "grade answers" shouldn't share a dependency tree). The judge LLM is Groq llama-3.3-70b-versatile, passed explicitly so RAGAS doesn't silently default to an OpenAI judge.

8. Honest "things I'd improve" (shows seniority)
Interviewers love when you volunteer known gaps. Real ones in this codebase:

Config drift: embedding_dim is 512 in code but the .env.example and comments still say 1536; LLM_PROVIDER defaults to groq in code but gemini in the env template. These should be reconciled.
A latent eval bug: score.py reads row["type"] but the dataset uses category — that would KeyError. The score.py docstring also says it uses Gemini embeddings while the code actually uses VoyageAI.
Synthesizer trace logs settings.openai_model regardless of the active provider — cosmetic but misleading in traces.
Scaling: no ANN index on pgvector, and ingestion is synchronous in the request path — both fine for MVP, both flagged as next steps.
History replay stores only question/answer, so citations/trace are empty on replayed history.
